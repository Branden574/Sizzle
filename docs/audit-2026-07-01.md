Git history shows plugin wiring was never committed (only commit d638121 touched these files) and the working tree is clean. Failure scenario: build/archive from this repo state via `cap:open:ios` → Xcode Archive or Android Studio (the normal store flow, which does NOT run `cap sync`) → iOS fails to compile because AppDelegate.swift line 3 `import FirebaseCore` resolves to nothing; Android builds but ships a binary where FirebaseMessaging/NativeBiometric/App plugins are 'not implemented' — enablePush() silently returns false, biometricAvailability() reports unavailable, the appStateChange re-lock never fires. Every native feature the tasks list marks 'completed' is dead in a fresh-clone or CI build.
  - **Fix:** Run `npx cap sync` in apps/web and commit the regenerated Package.swift, capacitor.config.json (packageClassList), capacitor.settings.gradle, and capacitor.build.gradle; add a CI check that `cap sync` produces no diff.
- [ ] **[HIGH/security]** Photo-post image URL check bypassable with .includes() — arbitrary external URLs accepted
  - `apps/api/src/routes/recipes.ts:104` — POST /recipes validates photo posts with `u.includes(`/storage/v1/object/public/videos/${userId}/`)`. Zod only requires a valid URL, so an authenticated user can submit `https://evil.example/track?p=/storage/v1/object/public/videos/<their-own-uuid>/x.jpg` — the substring match passes and the URL is stored in image_urls and served in every viewer's feed via buildCards (mappers.ts:209). This defeats the stated goal ('blocks posting arbitrary or someone else's URLs'): attacker-hosted images enable IP/UA harvesting of all viewers, off-platform illegal content that bypasses upload moderation, and content that can be swapped after posting.
  - **Fix:** Parse the URL and require an exact origin match against the Supabase project URL plus a path prefix check: `url.origin === SUPABASE_URL && url.pathname.startsWith(`/storage/v1/object/public/videos/${userId}/`)`.
- [ ] **[HIGH/bug]** Sign-out never unregisters the push token server-side (DELETE /me/push-token always 401s)
  - `apps/web/src/auth/useAuth.ts:156` — signOut() calls supabase.auth.signOut() first, which destroys the local session; only after the store flips to 'anon' does App.tsx:119 run disablePush(). disablePush() calls apiSend('DELETE','/me/push-token') via authHeaders() (apps/web/src/lib/api.ts:16-20), which now finds no session and sends no Authorization header, so requireAuth (apps/api/src/middleware/auth.ts:29-35) returns 401 and the catch in lib/push.ts:98 swallows it. The push_tokens row therefore survives every sign-out. The only remaining safety net is FirebaseMessaging.deleteToken(), which is also best-effort (silently caught, push.ts:104-108). Failure scenario: user A signs out on a device while offline (or deleteToken() rejects) -> the FCM token stays valid and bound to A in push_tokens -> the logged-out device (possibly now used by someone else) keeps receiving A's pushes ('X started following you', etc.) indefinitely, since server-side pruning only happens when FCM reports the token dead.
  - **Fix:** Call disablePush() (or at least the DELETE /me/push-token request) inside signOut() BEFORE supabase.auth.signOut(), while the access token is still valid; keep the App.tsx effect as a fallback only.
- [ ] **[HIGH/security]** Support-request intake has no dedicated rate limit; spam floods the privacy-request channel
  - `apps/api/src/routes/support.ts:26` — POST /support/requests is unauthenticated and relies only on the global limiter (300 req/min per IP, app.ts:50). Every accepted request inserts a row into support_requests with no dedupe or per-route cap. Meanwhile the admin view (apps/api/src/routes/admin.ts:366-371) is hard-capped at the 200 newest rows with no pagination or status filter. Failure scenario: one IP sends 300 junk requests/min (~432k/day); real GDPR/CCPA access/delete requests are pushed past the 200-row window and become invisible in the admin UI — a legal-compliance channel is silently DoS'd. The only bot defense is the honeypot, which is itself broken (separate finding).
  - **Fix:** Add rateLimit({ windowMs: 60_000, max: 3-5, name: 'support' }) to the route, and add pagination + status filtering (or at least order open-first) to GET /admin/support-requests.
- [ ] **[HIGH/security]** Rate limiting is ineffective on the actual Vercel serverless deployment
  - `apps/api/src/middleware/rateLimit.ts:13` — The limiter is an in-memory Map; the comment at line 11 says 'Fine for a single instance (Railway/Fly)', but the API deploys as a Vercel serverless function (apps/api/vercel.json + apps/api/api/index.ts). Each concurrent lambda instance has its own Map and cold starts reset it. Failure scenario: an attacker issuing concurrent requests fans out across N instances and gets N×max throughput; every limit in the app (global 300/min, dm 60/min, recipe-create 20/min, report 15/min, and the support-spam backstop) multiplies or resets, so comment/DM/report spam and support flooding are only nominally throttled. Also note identity() falls back to a single shared 'anon' bucket when x-forwarded-for is absent.
  - **Fix:** Back the limiter with a shared store (Upstash Redis / Vercel KV) keyed the same way, or use Vercel WAF/firewall rate rules; keep the in-memory version only for local dev.
- [ ] **[HIGH/bug]** Account deletion cascades orphan every denormalized counter (followers, like/comment/save counts, total_likes)
  - `apps/api/src/routes/me.ts:424` — DELETE /me (supabaseAdmin.auth.admin.deleteUser) and purge_expired_accounts() (supabase/migrations/20260620260000_moderation_repost.sql:56-79) rely purely on ON DELETE CASCADE. The cascade removes the user's rows in follows, reactions, comments, and saves, but none of the denormalized counters maintained by adjust_follow_counters/toggle_reaction/adjust_comment_count/adjust_save_count are corrected. Failure scenario: user A follows cook B, likes/comments/saves B's recipes, then deletes their account (or is purged after a ban). B's profiles.follower_count, profiles.total_likes and each recipe's like_count/comment_count/save_count stay permanently inflated with no source-of-truth rows backing them, and the drift compounds with every deleted account.
  - **Fix:** Before deleteUser/purge, run a SQL function that decrements counters from the user's actual rows (or add AFTER DELETE triggers on follows/reactions/comments/saves that adjust the counters, replacing the API-side adjust_* calls).
- [ ] **[HIGH/security]** Photo-post image URL check uses substring match, allowing arbitrary external hosts
  - `apps/api/src/routes/recipes.ts:104` — POST /recipes validates photo posts with u.includes(`/storage/v1/object/public/videos/${userId}/`) — a substring test, not a prefix test. userId is the caller's own id, so an attacker crafts images: ["https://evil.example/storage/v1/object/public/videos/<their-own-uuid>/x.jpg"] which passes zod's .url() and the includes() check, gets stored in recipes.image_urls, and is then served to every feed viewer (attacker-controlled content / phishing / IP-logging pixel). - [ ] **[HIGH/bug]** DM thread query returns the OLDEST 300 messages — new messages disappear in long threads
  - `apps/api/src/routes/messages.ts:131` — GET /messages/with/:userId does .order('created_at', { ascending: true }).limit(300) on messages. LIMIT applies after the ascending sort, so once a conversation exceeds 300 messages the endpoint always returns the first (oldest) 300 and every newer message is silently invisible to both participants on reload — the inbox preview (denormalized last_message_text) shows a message the thread view never displays.
